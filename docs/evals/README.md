# 维护者专用：独立冷启动评测协议

本目录用于改进 skill，不是应用适配执行手册。**不得被正常 skill 入口、路线文档或运行脚本导入，也不得进入四个应用 skill 导出包。** 维护者保管评测输入、原始记录和比较结果；执行者只接收脱敏后的本轮输入、原始源码和冻结的应用 skill 包。

离线解析、规则回归及导出检查不证明适配成功率或性能提高。历史组件日志仅供维护者提炼通用方法，不能成为分发的组件答案、补丁或执行提示。

## 1. 一轮是什么

一个 `run_id` 对应一个组件/版本、一次重复、一份冻结 skill 与输入及一个无历史答案的独立执行上下文。基线与候选、不同组件和每次重复各用新的 run_id；维护者用批次清单关联它们。批次可共用同一 skill 快照，但不能共享组件结论、适配副本或任务输出。为节省时间复用同一执行者继续修上一轮不属于独立冷启动。

固定循环如下：

1. **冻结**：维护者固定 skill 源码身份、导出包清单/哈希和本轮输入哈希，记录模型、工具、预算、原源码、原测试合同与资源条件。
2. **独立适配**：新的执行者从固定原始源码出发，按冻结 skill 完成调查、选路、构建及最小功能验证，再做约定范围验收。沿入口五步推进；只有命中症状才读取对应参考指南，不强制通读全部材料或凑探针数量。
3. **结束与审阅**：封存完整命令、日志、源码改动、生成映射、加载产物及测试记录。维护者复核功能是否真的完成，并将问题分成 skill、应用适配、上游、环境、执行偏差或未确定。
4. **修改候选**：只在候选分支改 skill 与离线回归；项目特例留在应用补丁中，历史原始证据只追加索引/勘误，不改写。
5. **新独立轮**：新 skill、新输入、资源合同或授权范围发生变化时使用新的 `run_id`，从同一固定原始源码重新开始；不得拿上一轮修好的组件继续跑来证明改进。
6. **对照真实效果**：比较实际完成率、失败构建、尝试、错误修改、成本与安全边界；加入未参与经验提炼的组件或版本作为 holdout。
7. **最后才考虑合并**：只有新独立轮的效果可核查、原合同不退步、无假通过及越界，且用户明确批准目标合并，才执行合并。协议、示例、离线测试或维护者意见均不构成合并授权。

同一轮 skill 全程不变。遇到 skill 缺陷时记录并阻塞相关工作，继续无依赖工作；不能修好冻结包再接着计分。安全问题需要停用时结束/中止本轮，保存已有计数，修复后另起新轮。应用源码的适配修改是本轮被测行为，允许在授权副本内进行；最终应用冻结后再改，则旧验收失效并须重建重测，不等于允许更换本轮 skill。

## 2. 维护者与执行者隔离

| 信息 | 维护者 | 独立执行者 |
| --- | --- | --- |
| 历史日志、补丁、组件决策、旧回执、此前生成树/二进制 | 可读，用于归因和提炼 | 不提供、不检索、不加载 |
| 组件历史调查/单轮计划及版本冲突结论 | 历史训练材料 | 不作为任务提示 |
| 冻结应用 skill 包及按症状加载的通用经验 | 固定身份 | 只读使用，不自行导出/更新 |
| 原源码、固定版本、公共原文档、原测试、约定范围 | 固定并校验 | 可读；适配只写授权副本 |
| 环境当前事实、用户真实约束与许可 | 整理且留出处 | 可用，但不得夹带解法或推定授权 |
| baseline/candidate 标签、holdout 归属、比较结论 | 私有评测台账 | 不提示预期胜负或答案 |

使用 [round-input.example.json](round-input.example.json) 制作输入；它是中立字段样例，不是 `route_preflight.py --request` 的请求体。`example_only: true`、尖括号占位符、未填身份/合同/授权都意味着不能启动执行。填写后仍须核验用户许可，不能把 JSON 的布尔值、旧计划勾选框或审阅方回复当作授权。真实地址、账号与路径只存在维护者受控的运行输入，不写回本目录的分发示例。

执行上下文仅给：本轮清洁简报、输入数据、冻结包、原始源码及允许的通用资料。不要把本 README、维护者计划、历史摘要或上轮会话拼进提示。若意外看到了历史答案，记录污染来源，将该轮标为 `contaminated`，不得并入主独立对照。

## 3. 冷启动与环境可比性

冷启动指**任务知识、源码和产物冷启动**，不是每轮重装系统或清空机器缓存。

- 每轮创建新的原源码校验副本、适配副本、生成目录、build、安装前缀、测试输出、命令证据及任务专用编译/JIT/扩展缓存命名空间。输出不得与 pristine 源码、skill 包或其他任务重叠；核对链接/挂载边界。
- 禁止复用旧组件决策/报告、补丁、HIPIFY/转换树、对象、wheel/so、旧安装及任务专用缓存。核实实际加载路径和产物哈希，路径不同本身不证明产物全新。
- **可复用同一已初始化基础环境**，条件是测量并记录等价性：系统/容器镜像、Python/Conda、DTK/编译器、框架及依赖身份、环境变量、设备/gfx/wave、配额与占用、缓存基线和采样时间。配置文本相同不等于环境实测等价。
- 保留共享下载缓存与公共依赖；不得 purge 共享缓存。若工具不能隔离任务缓存，记录命中、加载来源及残留影响；无法排除旧产物则本轮不满足冷启动。不能以默认禁用硬件缓存来伪造可比性。
- A/B 固定同一源码、合同、可用依赖、模型标识/配置、工具集、资源与预算；顺序随机化或交错，并记录并发/负载。不同条件不得直接合并成 skill 效果。重复次数及停止预算在看结果前确定，所有失败/中止轮保留，不能挑最好的一轮。
- 至少保留一个未参与规则提炼的组件或新版本。holdout 清单与选择依据由维护者保存；一旦据其结果改 skill，它就成为开发样本，需另留未见样本，不能重复称为盲测。

## 4. 远端执行边界

获得真实用户授权后，先读取用户的 `ssh-mcp-persistent-shell` skill。用 SSH MCP 的 `ssh_list_servers`、`ssh_session_list` 核实目标并复用会话；没有合适会话才 `ssh_session_start`，后续命令只通过同一 session ID 的 `ssh_session_send`。

使用正常交互式 Bash 和系统启动链，核实目标用户 `.bashrc` 已加载；确实缺失时查清启动链后仅初始化一次。进入容器用 `docker exec -it <实际容器名> bash`；核验节点、容器标志、用户、实际 `pwd`、shell PID、TTY、Conda/DTK 与任务所需工具。沿用已有配置，不强制版本，不改启动文件，不逐条重新 source 或 docker exec。

跨回合先确认 session 存在；失联后恢复同目标、目录与明确环境并核验。状态不明的构建/写入先查进程和日志，不盲目重放。不得改用一次性 `ssh_execute`、本地原生 SSH 或 `--noprofile --norc`；保持会话供后续使用，不关闭其他会话，也不承诺永久有效。

## 5. 执行合同与 tile 验证

三条路线保持独立：明确指定优先；含 CUDA 输入的 target 默认转码，纯 HIP 目标沿原生构建，不转码只接受显式选择。只调查所需能力，未知不是不支持；指定路线受阻不得静默切换。preflight 不执行编译、转换、安装或模式激活。许可不足就记 blocked，不将版本信息、能力探针或旧许可当作新授权。

持久修复落在授权适配副本的原始源码、构建脚本或版本化转换规则，不手改生成树作为最终成果。保留公共 API/ABI、格式/布局、输入副作用、原测试范围、独立 oracle、原始容差及非 HCU 路径；不以删测试、关功能、缩输入、CPU fallback 或全 skip 凑通过。最终应用快照与回执、构建、加载产物一一绑定；源码变化后重建重测，记录不得沿用。

HCU tile 默认优先 `tile=warpSize`，**只有实测 wave64 的目标才以 64 实现**。这是实现偏好，不是速度结论，也不是全仓 32→64。先判定原任务如何分组，同时审查任务到 lane 映射、mask/ballot 位宽、shuffle/reduction、共享/临时存储、block/grid、caller 覆盖与同步。`warpSize` 能否作为模板常量由实际工具链验证；必要时使用已核实的编译期值或架构分派。

格式宽度 **L**、公共布局及原逻辑任务语义保持不变。完整 wave 不能等价实现时，保留原逻辑 tile，采用 phase/串行循环；不得为了整 wave 重写格式合同。两种方案都须验证参与者进展、锁/内存可见性、原业务断言；适用的 wave64 用例覆盖 lane31/32/63、尾部、多个逻辑组争用及 caller grid。不能把所有超时归因于 tile，也不默认关闭缓存。cache/mask 实验必须有具体假设，诊断配置与最终验收分开，恢复约定配置后重测。

性能门槛：在相同 HCU、输入/dtype/L、构建、同步计时、预热、采样和负载下，对正确的整 wave 与 phase/其他合法基线保留原始样本、次数、中位数及离散程度；预先约定基于噪声的回退判据。没跑真实对照时写“性能未验证”，不称加速、不以偏好代替证据。无法进行对照则明确阻塞；不能将该项纳入已证明的性能收益。

## 6. 指标与状态口径

用 [round-metrics.example.json](round-metrics.example.json) 保存单 run 的维护者复核结果，组件分母通常为1；批次统计另按 run_id 汇总，并分别报告每个组件/版本及重复轮，不能覆盖单轮原始记录。它与应用 `adaptation-result` 回执、scope ledger 分开，不是已有 CLI 的输入。示例的 `null` 表示未测量/未知，不能替换为“0 次失败”或“100% 通过”。空数组只表示暂无记录。真实记录以 `run_id`、输入哈希和 skill 快照绑定，保留执行者原声明与审阅后判定。事件数组中的每项应有稳定事件ID、关联命令/尝试ID、原始证据引用和判定理由；功能数组应绑定冻结功能ID、原合同及逐阶段证据，不能只填汇总数。

| 指标 | 固定定义与证据 |
| --- | --- |
| 组件真实完成率 | `completed / assigned`；组件必须完成冻结范围的全部必需功能与阶段，不能只凭构建或账本检查 rc0。分母保留 blocked、skipped、partial、failed、not-run；分母为0则为 null |
| 必需功能完成率 | `verified_completed / frozen_required_units`；功能单位在运行前固定，不可事后拆小增加分子。分母同样保留阻塞与未运行项 |
| 状态分账 | 组件和功能分别列 completed/partial/failed/blocked/skipped/not-run，互斥且和为冻结总数；阶段状态另列。外部阻塞不算通过，也不直接归咎于 skill |
| 测试计数 | 原框架主项 passed/failed/skipped 分开，subtests、collection errors、required GPU executed/passed/skip/missing 另账；不把子断言充作主项，不丢 collection error |
| 可避免的失败全构建 | 先计所有完整构建调用及失败/超时，再由审阅方按当时可用信息判断可避免子集，关联命令/首错/应做的检查；不能以事后才知道的上游缺陷追责 |
| 尝试 | 每次假设→改动或诊断→验证给 attempt ID；记录全部、有效推进、无新证据重复和修复尝试，不强制“三个假设”。多次命令不能合并掩盖失败 |
| 错误修改 | 实际造成回退、改错文件/分支/语义/合同的补丁事件，关联差异与反证；后来撤回也保留计数，未经执行的建议不混作已修改 |
| 命令与 token | 统计实际调用、失败/超时、日志中的原始使用量与墙钟时间。token 来源及 input/output/cache_read/cache_write 分列；只得总数则保留原口径，未知不估填0 |
| 假通过 | 已宣称 completed/covered/passed 但证据不成立的事件；例如旧二进制、CPU 路径、漏必需GPU项、全skip、数值合同被削弱。纠正后仍保留原声明和事件 |
| 范围漂移/越界 | 原合同被缩减、未经批准改路线/资源/共享环境/受保护源码等事件；关联用户约束和写集。不能靠减少覆盖换取少命令 |
| 独立性与成本限制 | 污染、身份漂移、环境不等价、预算耗尽、人工干预均单列。耗尽预算不从分母删除；受污染轮保留但不作为独立效果证据 |

每条命令保留 cwd、argv、必要环境、开始/结束、完整 stdout/stderr、真实子进程 rc、信号/timeout 和产物身份。采集工具 rc、`tee` rc、日志摘要或子进程尚在运行均不等于被测命令成功。任务停止时先核查自身进程状态，不杀其他进程。长用例按预算和进展判定，不凭静默就当挂起。

## 7. 归因、比较与合并门槛

维护者逐项检查原始日志及补丁，分类允许多标签，但每项记录主因、证据、置信度和未确定部分：

- `skill`：通用规则/工具的缺陷、遗漏或误导，可用中立 fixture 复现。
- `application`：本轮应用适配补丁/实现的问题，不能自动推广为通用规则。
- `upstream`：原源码在固定基准已有的问题；未在基准复核则只是候选归因。
- `environment`：依赖、资源、工具链、设备或权限条件缺失；区分已测事实与猜测。
- `execution`：未遵守冻结 skill、误操作、错误统计或错误环境使用；与 skill 缺陷分开。
- `unknown`：证据不足，保留阻塞和下一项判别，不强选主因。

比较时先检查完整性与独立性，再逐组件/功能成对比较，报告全部重复轮的样本数、差值及波动，不以单轮最快结果推断普遍提升。执行环境、任务范围或模型/工具不同的轮标不可比，并解释影响；绝对完成率与可执行条件下的辅助指标都可列，但不能只展示排除 blocked 后的分母。

合并门槛：离线回归与四包边界检查通过；新独立轮相对固定基线出现可审计改善；原数值/测试/功能/路线合同没有退步；holdout 无未解释的退步；候选没有假通过、未授权越界或历史答案污染；涉及性能的结论满足第5节真实证据门槛；剩余未测项明确，且用户批准具体合并。任何一项缺证都交付候选与限制，不自动合并、提交、推送、安装或发布。

## 8. 发布与协议自检

这两个 JSON 是记录格式示例，不附带自动评测执行器或强制 schema 校验器。维护者填写真实输入后自行逐项核验；不要用不存在的 round/eval CLI。应用命令接口以冻结包的 `--help` 为准，不让执行者为追最新脚本更换包。

发布前应检查：

- 示例可被标准 JSON 解析，所有未运行结果仍为 `not-run`/`null`，无真实组件答案、补丁、私有运行路径或凭据。
- 应用入口、`references/` 与运行脚本不依赖 `evals/`；导出清单和重定位包中不含本目录、外部维护计划或历史记录。维护者源码仓的维护说明可以链接本协议，不使其成为执行依赖。
- 快照清单记录文件哈希；冻结前后字节一致。输入哈希放在外部清单，避免文件自哈希循环。
- 真实运行前确认授权、预算、原始范围、holdout、等价环境证据及空白任务目录；示例验证本身不是运行通过。
